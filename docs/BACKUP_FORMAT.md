# Portable encrypted backup format version 1

SuikaAuthenticator backups are independent, password-encrypted containers. They can be restored on Linux or Android without the source device, source vault password, Android Keystore key, or biometric enrollment. The backup password is chosen when exporting and is not changed when the live vault password changes.

The backup contains the versioned SuikaAuthenticator account database. This preserves account identifiers, issuer and label fields, TOTP/HOTP mode and parameters, HMAC algorithm, digit count, HOTP counters, favorites, groups, and OTP secrets.

## Binary layout

All integers are unsigned and big-endian. Version 1 has no optional padding, extension records, or trailing bytes.

| Offset | Length | Field | Description |
|---:|---:|---|---|
| 0 | 8 | Magic | ASCII bytes `SUIKABAK` |
| 8 | 2 | Format version | `1` |
| 10 | 1 | KDF identifier | `1` = Argon2id v1.3 |
| 11 | 1 | AEAD identifier | `1` = XChaCha20-Poly1305 |
| 12 | 2 | Flags | Reserved; must be zero |
| 14 | 4 | Argon2 memory | KiB |
| 18 | 4 | Argon2 iterations | Pass count |
| 22 | 4 | Argon2 lanes | Parallelism parameter |
| 26 | 32 | Salt | Random password KDF salt |
| 58 | 24 | DEK-wrap nonce | Random XChaCha20 nonce |
| 82 | 48 | Wrapped DEK | 32-byte DEK plus 16-byte tag |
| 130 | 24 | Payload nonce | Random XChaCha20 nonce |
| 154 | 4 | Payload ciphertext length | Includes 16-byte authentication tag |
| 158 | Variable | Encrypted payload | Encrypted account database |

The fixed header length is 158 bytes. The maximum plaintext payload is 16 MiB; the ciphertext can be at most 16 MiB + 16 bytes. The parser checks the complete length and all attacker-controlled fields before invoking Argon2id or allocating the payload.

## Key hierarchy

1. Validate the supplied plaintext as a complete versioned SuikaAuthenticator account database.
2. Generate a fresh random 256-bit DEK and 256-bit salt.
3. Derive a 256-bit KEK from the user-supplied backup password with Argon2id v1.3.
4. Encrypt the DEK with XChaCha20-Poly1305 under the KEK.
5. Encrypt the account database with XChaCha20-Poly1305 under the DEK.

The initial production KDF profile is 128 MiB, three iterations, and four lanes. The parser accepts only the bounded application range: 64–128 MiB, 1–3 iterations, and 1–4 lanes. Invalid values are rejected before KDF work. The backup password uses the same input length limit as the vault master password.

The backup uses a fresh DEK, salt, and both AEAD nonces for every export. It does not reuse the live vault's DEK, KEK, salt, or nonces.

## Associated data

DEK-wrap AAD consists of the domain string `SuikaAuthenticator/backup/v1/dek-wrap\0` followed by the complete 58-byte fixed prefix (magic, version, algorithm identifiers, flags, Argon2 parameters, and salt).

Payload AAD consists of the domain string `SuikaAuthenticator/backup/v1/payload\0`, the complete 58-byte prefix, the DEK-wrap nonce, the wrapped-DEK ciphertext including its authentication tag, and the four-byte payload ciphertext length.

The nonce for each ciphertext is also supplied as the nonce input to XChaCha20-Poly1305. Fresh nonces are generated by the operating-system CSPRNG. Randomness failure aborts export.

## Parsing and restore rules

- Reject invalid magic, unsupported version, unsupported algorithm identifiers, nonzero reserved flags, malformed lengths, and trailing bytes.
- Validate Argon2 parameters before invoking the KDF.
- Authenticate both the wrapped DEK and encrypted account database before returning plaintext.
- Wrong passwords and authenticated-data failures return the same generic restore error.
- Validate the decrypted database, all records, and all account parameters before returning it to the platform frontend.
- Restore replaces the current account database only after successful decryption, validation, and encrypted vault persistence. A failed restore must leave the current vault and in-memory account list unchanged.
- Never write decrypted account data to a temporary file. Export files contain ciphertext only.

A backup is a portable transfer/recovery file, not an automatically synchronized copy. The user must retain the backup password separately and protect the backup file from unauthorized access. If the backup password is lost, the backup cannot be decrypted.
